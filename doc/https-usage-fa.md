# استفاده از HTTP و HTTPS روی Commodore 64 Ultimate

هر دو از رابط فرمان موجود Ultimate، یعنی target شمارهٔ ۶، استفاده می‌کنند.
در برنامهٔ C64، آدرس را از `http://` به `https://` تغییر می‌دهیم؛ ساخت درخواست،
headerها، body، اجرای درخواست و خواندن پاسخ همان مسیر قبلی را دارند.
این قابلیت برای اتصال خروجی برنامهٔ C64 به سرور است. صفحهٔ مدیریت خود دستگاه
در شبکهٔ محلی با این تغییر به یک وب‌سرور HTTPS تبدیل نشده است.

## نمونهٔ یکسان برای هر دو روش

این دو آدرس در تست واقعی دستگاه، پاسخ یکسان `{"ok":true}` دادند:

```text
HTTP:  http://httpbingo.org/base64/eyJvayI6dHJ1ZX0=
HTTPS: https://httpbingo.org/base64/eyJvayI6dHJ1ZX0=
```

مراحل مشترک:

1. با `HEADER_CREATE` یک درخواست GET و URL بساز؛ handle برگشتی را نگه دار.
2. headerهای لازم را با `HEADER_ADD` اضافه کن. برای سرور نمونه، User-Agent
   می‌فرستیم؛ نبودن آن در آزمایش قبلی به پاسخ ۴۰۲ از همین سرور منجر شد.
3. درخواست را با `DO_EXCHANGE_OBJ` برای JSON یا `DO_EXCHANGE_RAW` برای بایت‌های
   خام اجرا کن. در GET این مثال body درخواست نداریم.
4. پاسخ را بخوان و سپس handleهای متعلق به درخواست را آزاد کن.

نام‌های بالا نام فرمان‌های موجودند، نه تابع‌های تازهٔ BASIC یا یک کتابخانهٔ جدید.

## فرمان‌های واقعی برای برنامه‌نویسی C64

تمام اعداد جدول هگز هستند. متن داخل کوتیشن، بایت‌های ASCII است؛ کوتیشن‌ها
ارسال نمی‌شوند. `H`، `RH` و `RB` یک بایت handle هستند که باید از پاسخ خوانده شوند؛
مقدارشان را ثابت فرض نکن. `00` انتهای رشته است. URL را به ASCII بفرست؛
رشتهٔ PETSCII صفحه‌کلید C64 لزوماً همان بایت‌ها را ندارد.

| کار | بایت‌های فرمان | نتیجه |
| --- | --- | --- |
| ساخت GET | `06 11 01 "URL" 00` | یک بایت: `H`؛ وضعیت `000 OK` |
| افزودن header نمونه | `06 13 H "User-Agent: Ultimate-HTTPS-hardware-test/1.0" 00` | وضعیت `000 OK` |
| گرفتن JSON | `06 31 H FF` | دو بایت: `RH RB`؛ برای مثال وضعیت `200 OK` |
| خواندن کل JSON | `06 2A RB 00` | نمایش باینری نوع‌دار JSON |
| خواندن فقط ok | `06 2A RB "ok" 00` | `02 01`: نوع boolean و مقدار true |
| آزاد کردن header درخواست | `06 12 H` | وضعیت `000 OK` |
| آزاد کردن header پاسخ | `06 12 RH` | وضعیت `000 OK` |
| آزاد کردن body پاسخ | `06 22 RB` | وضعیت `000 OK` |

`01` در HEADER_CREATE یعنی GET و `FF` در این مثال یعنی body درخواست نداریم.
فرمان `06 10` همهٔ handleهای HTTP را آزاد می‌کند؛ در یک مثال مستقل می‌توان
ابتدا و انتها از آن استفاده کرد، ولی در برنامه‌ای با چند درخواست فعال، منابع
همهٔ آن‌ها را پاک می‌کند. برای هر مرحله ابتدا وضعیت و طول پاسخ را بررسی کن؛
در شکست درخواست، بایت‌های پاسخ را به‌عنوان handle مصرف نکن.

پاسخ نوع‌دار کل شیء در آزمایش واقعی هر دو روش دقیقاً این بود:

```text
04 01 02 6F 6B 02 01
```

این داده نمایش داخلی شیء `{"ok":true}` است؛ JSON متنی نیست.

## دریافت دادهٔ خام

بعد از ساخت header، به جای `06 31 H FF` این فرمان را بفرست:

```text
06 32 H FF
```

کانال داده، بایت‌های body را می‌دهد؛ در همین مثال متن `{"ok":true}`.
کانال وضعیت، ابتدای پاسخ HTTP شامل خط وضعیت و headerها را تا سقف ۲۵۵ بایت
می‌دهد. برای بررسی headerهای بیشتر در پاسخ JSON، از handle پاسخ و فرمان‌های
HEADER_QUERY/HEADER_LIST موجود استفاده کن.

body ممکن است چند بخش داشته باشد. هر بخش تا ۸۹۵ بایت است؛ تا رسیدن به
Data Last از سازوکار DATA_ACC و ادامهٔ پاسخ موجود استفاده کن. پایان را از
وضعیت رابط تشخیص بده، نه فقط طول داده: پاسخ دقیقاً ۸۹۵ بایتی می‌تواند یک
بخش پایانی خالی هم داشته باشد. بعد از خواندن بخش آخر نیز آن را acknowledge کن.
برای نمونه، پاسخ ۲۰۴۸ بایتی در آزمایش واقعی به صورت `895 + 895 + 258` رسید.

ارسال فرمان و خواندن بایت‌ها همان رابط رجیسترهای موجود است؛ نمونهٔ اجرایی
6502 در `tests/e2e/io/command_interface/uci_agent.asm` و راه‌انداز آن در
`tests/e2e/lib/uci_native.py` قرار دارد. آن agent ابزار تست است؛ کتابخانهٔ
عمومی تازه‌ای به برنامهٔ C64 اضافه نکرده‌ایم.

## اجرای نمونه از کامپیوتر

ابزار موجود `tools/c64u_https/smoke.py` برنامهٔ کوچک 6502 را روی C64 اجرا
می‌کند و فرمان‌ها را واقعاً از خود C64 می‌فرستد. Python روی کامپیوتر نقش
راه‌انداز و ثبت نتیجه را دارد. این کار برنامهٔ فعلی C64 و بخشی از RAM آن را
جایگزین می‌کند؛ firmware نصب نمی‌کند. پس از پایان، برنامهٔ تست در RAM می‌ماند؛
با Reset معمولی C64 می‌توان از آن خارج شد.

از ریشهٔ مخزن در Linux یا WSL، با جایگزینی DEVICE_IP با آدرس دستگاه:

```sh
python3 tools/c64u_https/smoke.py --host DEVICE_IP --url http://httpbingo.org/base64/eyJvayI6dHJ1ZX0= --url https://httpbingo.org/base64/eyJvayI6dHJ1ZX0= --expect-hex 0401026f6b0201 --output /tmp/demo-http-https.json
```

ابزار هر دو روش را اجرا می‌کند و یکسان بودن داده را بررسی می‌کند. برای دریافت
خام، `--raw` را اضافه کن و مقدار `--expect-hex` را به
`7b226f6b223a747275657d` تغییر بده؛ این همان بایت‌های متن JSON است.

## تفاوت تنظیمات و خطاها

| موضوع | HTTP | HTTPS |
| --- | --- | --- |
| URL | `http://...` | `https://...` |
| پورت پیش‌فرض | 80 | 443 |
| target و فرمان‌ها | 6 و فرمان‌های HTTP | همان‌ها |
| header، body و handleها | روش موجود | همان روش |
| رمزنگاری و بررسی هویت سرور | ندارد | داخل firmware انجام می‌شود |
| زمان همگام و گواهی قابل اعتماد | برای TLS لازم نیست | لازم است؛ مدیریت با firmware است |

در هر درخواست لازم نیست گواهی یا ساعت را به فرمان‌ها اضافه کنی. شبکه، DNS،
زمان همگام و کنترلر سازگار باید در دستگاه آماده باشند. در HTTPS نام میزبان
باید با گواهی سرور تطابق داشته باشد. خطای TLS، ساعت یا اتصال فعلاً به صورت
وضعیت عمومی `503 SERVICE UNAVAILABLE` برمی‌گردد؛ این پیام علت دقیق را مشخص
نمی‌کند. در شکست HTTPS، خودکار به HTTP برنمی‌گردیم. مهلت کل مبادلهٔ HTTPS
۱۵ ثانیه است؛ نباید این حد را برای مسیر HTTP قدیمی هم تضمین‌شده فرض کرد.

## آزمایش‌های بعدی به ترتیب اولویت

1. درخواست‌های متوالی طولانی‌تر و ثبت نرخ خطا و مصرف حافظه؛ یک درخواست HTTP
   اولیه ۵۰۳ داد و علتش هنوز مشخص نشده است. پاسخ‌های کوتاه/بلند و HTTP/HTTPS
   را ترکیب کنیم و برگشت به حالت سالم بعد از شکست را بسنجیم.
2. قطع و وصل Wi-Fi، DNS ناموفق، سرور کند و پایان مهلت؛ روی سخت‌افزار بررسی
   کنیم درخواست معطل نماند و درخواست بعدی بتواند کار کند.
3. رفتار زمان نامعتبر/قدیمی، پاسخ‌های HTTP ناقص یا بدشکل و فشار صف‌ها؛ بخشی
   از این‌ها تست میزبان دارند، ولی پوشش کامل parser و رفتار سخت‌افزار باقی است.
4. برای آمادگی انتشار: اندازه‌گیری حافظه و پشته، راه‌اندازی مستقل کنترلر و
   پایداری شمارندهٔ ذخیره‌شده. آزمایش خرابی نوشتن flash و قطع برق هنگام نوشتن
   به محیط آزمایش با مسیر بازیابی آماده نیاز دارد.

برای نمونه‌های فعلی نصب دیگری لازم نیست. نتیجهٔ آزمایش‌های انجام‌شده و
محدودیت‌های آن‌ها در `https-device-validation.md` ثبت شده است.
